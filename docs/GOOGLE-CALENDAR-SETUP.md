# Google organizer setup

This is the configuration needed by the existing server-side Calendar adapter. It is separate from Gmail SMTP: the Gmail App Password cannot authorize Calendar or Meet. No Google project, OAuth grant, event or room was created while preparing these instructions.

1. Sign into the intended organizer account in Google Cloud Console and select/create the Git Tutor project. Enable **Google Calendar API**. Keep any development rehearsal project separate from production.
2. Configure Google Auth Platform branding, audience, support contact and data access for the actual application. The implemented scopes are `openid`, `email` and `https://www.googleapis.com/auth/calendar.events`. Learners do not need to grant Calendar access merely to use the portal.
3. Create an OAuth client of type **Web application** for this ordinary application flow. Configure the exact authorized redirect URI as `https://FINAL_APPROVED_HOST/api/calendar/google/callback`. The hostname must match `APP_BASE_URL`; a temporary deployment URL is not the production callback.
4. Privately provide `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` through the deployment secret manager. Provide `GOOGLE_CALENDAR_ID` for the organizer-controlled calendar. Do not send a Google password or manually pasted access/refresh token. An API key or desktop-app client does not substitute for this web client.
5. After the selected host is configured, sign into Git Tutor as the owner/admin and use its Calendar connection action. The existing application requests offline consent with state/PKCE, verifies organizer identity and encrypts refresh credentials server-side. The organizer completes Google's consent step interactively.
6. Verify the granted calendar, refresh behavior, event creation/update/cancellation, duplicate/unknown outcome reconciliation, tutor hosting, and permitted external learner admission using explicitly approved synthetic test attendees. Actual invites are external messages and require approval of recipients/content. Record received notifications separately from API acceptance.
7. Confirm the organizer's meeting entitlement supports90–105minute group sessions. Free Meet's60-minute limit with three or more participants is insufficient; select an appropriately entitled existing account or approve a different free provider before group activation.

An external OAuth app left in **Testing** issues refresh credentials that expire after seven days for these Calendar scopes. A short rehearsal can use test users, but production publishing/verification must match the real audience and Google's policies. A commercial tutoring service is not automatically exempt merely because the initial organizer count is small. Do not describe a seven-day test connection as permanent production readiness. [Google OAuth expiry](https://developers.google.com/identity/protocols/oauth2), [audience settings](https://support.google.com/cloud/answer/15549945?hl=en), [verification exceptions](https://support.google.com/cloud/answer/13464323?hl=en).

Current standard Calendar API usage is available without additional cost subject to quotas. Google documents planned billing above standard thresholds, so do not enable billing or request a paid quota increase under the owner's free-only instruction. This API allowance is separate from Meet's meeting-length entitlement. [Calendar quotas and pricing](https://developers.google.com/workspace/calendar/api/guides/quota), [Meet limits](https://support.google.com/meet/answer/7317473?hl=en).

Implementation references checked15November2026: [web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [web application client creation](https://developers.google.com/workspace/calendar/api/quickstart/js). The application uses the server-side authorization-code exchange with a private client secret; browser-only quickstart credentials are not its deployment configuration.
