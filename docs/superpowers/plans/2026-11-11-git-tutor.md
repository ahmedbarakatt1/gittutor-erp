# Git Tutor implementation plan

> For agentic workers, use the installed subagent-driven-development or executing-plans skill when available. Execute the same task, verification and review sequence directly in Codex when those skills are unavailable.

## Goal

Build the Git Tutor website and operations platform with confidential tutor compensation, correct group pricing, package entitlements, reconciled payments and auditable teaching-to-payout workflows.

## Architecture

Use one modular Next.js application backed by Supabase Auth, PostgreSQL and private Storage. Narrow database commands own business transactions. A durable Node.js worker performs provider integration and delivery after the related records and outbox events commit.

## Tech stack

TypeScript, Next.js App Router, Supabase, a Node.js worker, Vitest and Playwright. Select compatible supported versions during T01 and commit the lockfile. Follow an existing compatible repository's established tooling and record the command/path mapping.

## Global constraints

- Currency starts with EGP. Monetary values use integer minor units. Instants use UTC and the business timezone is Africa/Cairo.
- Group sizes 2, 3 and 4 have customer prices 57500, 55000 and 50000 minor units per seat.
- Internal tutor fee bands are 45000–45000, 60000–65000 and 70000–75000 minor units. Each confirmed occurrence has one exact approved fee.
- Customer responses use explicit allowlists. Internal compensation, margins, payout destinations and operational notes stay in privileged projections.
- Package quantities use integer credit_quanta and 1000 quanta per standard session, with explicit base duration and eligibility.
- Fixtures are synthetic. The workbook supplies business cases.
- A published offer has a complete approved commercial policy. Synthetic policies may be published only inside isolated development/test environments.
- Staff and guardian scope are checked against current database records. Sensitive mutations derive the actor from verified authentication.
- Financial postings retain their original values. Corrections use linked adjustments and reversals.
- Every mutating command has persistent idempotency and an appropriate version/conflict contract.
- All original acceptance-case IDs and added regressions map to an owning test or documented manual check.

## Review focus

1. A guardian contact can represent several learners. T02 and T10 test distinct identities, revocation and additive export semantics.
2. A receipt may arrive after a hold expires or cover several obligations. T04 and T06 test late funds, capacity changes and allocation conservation.
3. A shortened class and an individual early departure have different remedies. T05 and T08 test exact entitlement and fee outcomes under an explicit policy.
4. A provider timeout can conceal a successful payout or event creation. T07–T09 test unknown outcomes, stable provider identities and reconciliation before retry.
5. A repeat inquiry can cross a Cairo month boundary and earlier attendance can be missing. T12 tests lifetime first-touch selection, local date cutoffs and unknown history.

## Dependency checkpoint

T01 provides the durable outbox schema, atomic enqueue and worker lease primitive. Each later command writes its event in the same database transaction as its business records. T09 adds notification routing and delivery on that foundation.

T04 implements and tests holds, quotes, schedules, amendment proposals and the confirmation contract. T05 implements and tests entitlement movements and remedy-reservation contracts. After their independent foundation checks pass, mark each `awaiting_T06_integration` and continue. T06 implements settled funding, allocations and refund reservations, then integrates funded confirmation, committed charge/fee amendments and shared cash/entitlement remedy limits. T06 closes only after the combined T04–T06 transaction and concurrency tests pass. Then mark all three verified. Keep the dependent actions unavailable until their real transaction implementation is complete.

On resumption, select the earliest unfinished task whose prerequisites are ready. This checkpoint permits forward progress while retaining the incomplete checks and their owning tasks.
